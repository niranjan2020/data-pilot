# Data Pilot Architecture & Technical Specification

## Architectural Overview

Data Pilot is structured as a **Modular Monolith** adhering to Clean Architecture / Hexagonal principles (Ports & Adapters).

```
                      ┌──────────────────────────┐
                      │      HTTP API Layer      │
                      │  (FastAPI, Endpoints)    │
                      └────────────┬─────────────┘
                                   │
                      ┌────────────▼─────────────┐
                      │    Application Layer     │
                      │  (Services, Orchestrator)│
                      └────────────┬─────────────┘
                                   │
                      ┌────────────▼─────────────┐
                      │       Domain Layer       │
                      │  (Protocols & Models)    │
                      └────────────▲─────────────┘
                                   │  implements
              ┌────────────────────┴────────────────────┐
              │                                         │
┌─────────────┴─────────────┐             ┌─────────────┴─────────────┐
│    Database Adapters      │             │       LLM Adapters        │
│ (PostgreSQL, Snowflake)   │             │ (Gemini, OpenAI, Local)   │
└───────────────────────────┘             └───────────────────────────┘
```

### 1. Dependency Inversion

All high-level application modules depend solely on abstractions declared in `datapilot.domain.interfaces`. Concrete implementations in `datapilot.infrastructure` plug into these abstractions without coupling the core logic to any third-party SDK or database driver.

### 2. Core Protocol Contracts

| Interface | Module | Purpose |
| :--- | :--- | :--- |
| `DatabaseProvider` | `datapilot.domain.interfaces.database` | Connection check, schema reflection, and query execution |
| `LLMProvider` | `datapilot.domain.interfaces.llm` | Text generation and structured output parsing |
| `MetadataProvider` | `datapilot.domain.interfaces.metadata` | Enriched business metadata persistence |
| `SQLGenerator` | `datapilot.domain.interfaces.sql_generator` | Synthesis of SQL from question + schema |
| `SQLValidator` | `datapilot.domain.interfaces.sql_validator` | Strict safety, AST parsing, and read-only checks |

### 3. Safety Guarantees

Data Pilot enforces a strict security perimeter:
- **No Direct Execution of Raw LLM Output:** SQL queries generated by the LLM must pass through the `SQLValidator` before reaching the `DatabaseProvider`.
- **Read-Only Enforcement:** DDL (`DROP`, `ALTER`, `CREATE`) and DML (`UPDATE`, `DELETE`, `INSERT`) operations are rejected by default.
- **Query Timeout & Limit Safeguards:** Execution timeouts and result size caps prevent database exhaustion.

### 4. Evolution Towards SaaS

When enterprise or SaaS requirements emerge in the future, the open-source core will remain untouched. A separate wrapper service will handle multi-tenancy, authentication tokens, and billing, delegating core NL-to-SQL workflows to Data Pilot via standard Python calls or gRPC/HTTP endpoints.
